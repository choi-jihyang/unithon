# 화면별 구현 기능 정의

버전 0.1 · 프로토타입 기준: [`demo.html`](./demo.html)
관련 문서: [`prd.md`](prd.md) (제품 개요/데이터모델/API 초안)

이 문서는 `demo.html`의 메뉴(F1~F6) 단위로, 각 화면이 실제로 무엇을 할 수 있어야 하는지를 정리한다. `demo.html`의 필수/선택 배지 구분은 유지하되, 여기서는 필수로 개발할 화면의 세부 동작 스펙에 집중한다.

---

## F1. 연동수집 메뉴

대상 화면: `1-1` 연동 설정 · `1-3` 수동 결정 기록

### 1-1. 연동 설정
- 유저(담당자) 계정별로 4개 연동 데이터 소스(GitHub / Slack / Jira / Notion)를 각각 **활성화/비활성화** 토글할 수 있어야 함.
- 연동 상태는 유저마다 독립적으로 저장 (사용자 A가 Slack을 꺼도 사용자 B에는 영향 없음).
- 실제 외부 API 인증/수집 로직은 MVP 범위 밖([`prd.md` 1-3](prd.md))이므로, 이 화면은 **토글 상태 저장까지만** 구현하고 실제 수집은 연결하지 않는다.

### 1-2. 수집 로그 뷰어 — 제거 결정 (2026-08-25)
- 타임라인식 로그 뷰어 UI를 화면에서 제거하기로 결정.
- 관련하여 1-3의 "로그 자동 반영" 요구사항도 함께 삭제 (아래 참고).

### 1-3. 수동 결정 기록
- 입력 필드: 대상 프로젝트/사례, 결정 내용, 이유, 근거(선택) — `prd.md` F1 입력 필드 정의와 동일.
- 제출 시 그래프 노드·엣지 생성 (`prd.md` 데이터 모델 참고).
- ~~1-2 수집 로그에 즉시 반영~~ — 1-2 제거로 해당 사항 없음. (제출 성공 알림 방식 필요 여부는 미결정)
- 실제 API 연동이 없는 MVP에서는 이 폼이 그래프 생성의 실질적 입력 경로이므로, 별도 예외 취급 문구는 제거하고 정상 플로우로 다룬다.

## F2. 이관 메뉴

대상 화면: `2-1` 이관 목록 · `2-2` 이관 실행 · `2-3` 이관 이력

### 권한
- **팀장급 이상만 이관을 실행**할 수 있음.
- 팀장급 이상만 이 메뉴군을 **조회**할 수 있도록 하는 세부 권한 분리(역할별 메뉴 노출 제어)는 **고도화 단계**로 미룬다. MVP에서는 "이관 실행" 버튼 동작 자체만 팀장급 계정 기준으로 확인하면 됨.

### 2-2. 이관 실행 (필수)
- 팀장급 계정이 "담당자 이관" 버튼 클릭 시:
  1. `ownership_transitions` 레코드 생성 (기존 담당자 → 신규 담당자)
  2. 대상 사례(들)의 담당자 필드 갱신
  3. **이관 즉시, 신규입사자(후임자) 계정이 해당 사례의 맥락 카드(F3)를 조회할 수 있도록 접근 권한이 갱신**되어야 함 — 이관 전에는 후임자가 해당 사례에 접근 불가.

### 2-1 / 2-3
- 이관 목록: 이관 대상 담당자와 보유 사례 리스트 (선택 구현).
- 이관 이력: 언제/누가/누구에게 이관됐는지 감사 로그, 조회 전용 (선택 구현).

## F3. 맥락카드 메뉴

대상 화면: `3-1` 사례 상세 페이지 · `3-2` 빈 상태 · `3-3` 근거 원문 확장

### 카드(노드) 관리
- 맥락 카드(결정/이유/근거 노드)는 **등록 후에도 수정**할 수 있어야 함 — 현재 프로토타입은 읽기 전용이므로 편집 UI 추가 필요.
- 노드를 수정할 때 **누가/언제/무엇을 바꿨는지(계정 정보 포함) 이력이 남아야** 함 — 새 담당자가 과거 기록을 덮어썼는지 추적 가능해야 하므로.

### 댓글/코멘트 (신규)
- 각 노드(카드) 단위로 **댓글 스레드**를 달 수 있으면 좋음 — 후임자가 "이 결정 왜 이렇게 했나요?" 같은 코멘트를 카드에 바로 남기는 용도.
- 프로토타입에 해당 화면이 없으므로, `3-4` (가칭 "카드 댓글") 화면 추가를 검토.
- F4(질문 메뉴)와 기능이 겹칠 수 있어, 최종적으로는 "카드 댓글 = 특정 노드에 달리는 짧은 코멘트" / "질문 메뉴 = 별도 트래킹되는 정식 Q&A"로 역할을 구분해야 함.

## F4. 질문 메뉴

대상 화면: `4-1` 질문하기 입력 · `4-2` 질문 이력 목록

### 4-1. 질문하기 입력
- 퇴사자/입사자(기존 담당자·후임자) 모두 질문을 등록할 수 있어야 함.
- 등록된 질문에 대한 **답변 작성** 기능 필요 — 답변자는 기존 담당자 또는 관리자. (프로토타입에 답변 UI 없음 → 추가 필요)
- **현재 프로토타입에 없는 입력 필드**:
  - 프로젝트명/사례명 (어떤 맥락에 대한 질문인지)
  - 질문 분야 선택 (카테고리 드롭다운 — 예: 결정배경/기술적근거/일반 등)

### 4-2. 질문 이력 목록
- 질문 이력을 **정렬(sorting)** 할 수 있어야 함 — 최소한 날짜순/프로젝트별/답변여부별 정렬 지원.
- 답변 여부를 목록에서 바로 구분할 수 있어야 함 (미답변/답변완료 상태 표시).

## F5. 성과 메뉴 (리포트)

대상 화면: `5-1` 요약 지표 카드 · `5-3` 전체 그래프 현황

- 사실상 리포트 화면. 현재 프로토타입 구조(지표 카드 + Before/After 비교)를 기본으로 하되, **최종 화면 구조는 변경될 수 있음** — 세부 스펙은 추후 확정.
- 현재 확정된 지표: 인수인계 문서 작성 시간, 질문 미발생률, 탐색 응답 속도 (`prd.md` 8장 성공 지표와 연결).

## F6. AI요약 레이어

대상 화면: `6-1` 요약 배지 카드

- 현재는 "원문이 길 때 조건부로 요약을 보여주는" 용도로만 한정.
- **원문 요약 외 활용처 추가 검토 필요** — 예를 들어 단순 요약을 넘어서는 방향성 파악이 필요함.
- 후보 방향: 추후 LLM을 도입해 **맥락 카드에 대해 자유롭게 질문하는 대화형 메뉴**로 확장 (F4 질문 메뉴와는 별개로, 카드 내용을 근거로 LLM이 답하는 방식). MVP 범위는 아니며 로드맵 항목으로 기재.

## 요약 — 추가/신규 개발이 필요한 부분

| 메뉴 | 프로토타입 대비 추가 필요 사항 |
|---|---|
| F1 연동수집 | 연동 소스별 유저 단위 토글 저장, 수집 로그 다중선택 삭제, 1-3→1-2 자동 연동 |
| F2 이관 | 팀장급 권한 체크(실행 단위), 이관 시 후임자 접근권한 즉시 갱신 |

## 추가 고려사항 (개발 관점)

아직 스펙이 확정되지 않아 개발 착수 전 결정이 필요한 항목들.

- [ ] **연동수집(F1) 항목별 데이터가 어떤 형태로 떨어지는지 정의**
      GitHub(커밋/PR)·Jira(필드/상태전이)·Figma(댓글/버전이력)·Slack(전용채널/리액션/슬래시커맨드) 등 소스마다 원본 payload 구조가 다름. 각 소스별로 "무엇을/왜/근거"로 매핑되는 필드를 스키마로 확정해야 수집 로그(1-2)와 그래프 노드 생성 로직을 붙일 수 있음.

- [ ] **수집 로그 → 맥락카드 자동생성 시, 카드의 제목/세부항목 구성 방식 정의**
      로그 1건이 그대로 카드 1개가 되는 게 아니라면, 여러 로그를 묶어 하나의 카드(제목 + 결정/이유/근거 노드들)로 구성하는 기준이 필요함. 제목을 어디서 뽑을지(커밋 메시지 요약? PR 제목? AI 요약?), 세부항목을 어떤 단위로 쪼갤지 결정 필요.

- [ ] **질문(F4)과 맥락카드(F3)를 매핑하는 구조 검토**
      "이 질문이 어떤 카드/노드를 보고 나온 질문인지" 연결되면, 카드가 놓친 지점을 파악하는 데 유용함(F5 지표와도 연결). 질문 등록 시 대상 카드(또는 노드)를 선택/자동매칭하는 방식 설계 필요.

- [ ] **AI요약(F6)을 LLM 기반 자연어 질의응답으로 고도화하는 방향 검토**
      현재는 원문 요약 배지 수준. 카드 내용을 근거로 자유 질문에 답하는 대화형 인터페이스로 확장할지, 확장한다면 F4 질문 메뉴와 역할을 어떻게 나눌지(사람 답변 vs LLM 답변) 결정 필요.
