# AI 코드 신뢰 / 테스트·QA 컨벤션

이 프로젝트는 Claude로 구현한다. 생성형 에이전트가 만든 코드를 사람이 라인 단위로 검수하기 어렵다는 전제에서, 신뢰의 근거를 **검증 체계**로 옮긴다.

## 원칙
1. **생성자 ≠ 검증자** — 코드를 짠 세션이 자기 코드를 "됐다"고 승인하지 않는다. 검증은 **분리된 컨텍스트**(새 Claude 세션/서브에이전트, 또는 동료 리뷰)가 한다.
2. **불변식은 사람이 정의** — AI가 못 게임하는 속성을 구현 전에 명시한다. (예: "포인트 잔액은 음수가 될 수 없다", "출금 시 잔액 차감은 원자적이다", "출석 적립은 하루 1회".)
3. **테스트만 믿지 않는다** — 유닛·통합 테스트 + 적대적 QA + 보안 점검의 다층으로 신뢰한다.

## 요구사항
- 기능/변경을 시작할 때 **수용기준·불변식·테스트 대상**을 먼저 적는다(PR 본문 또는 작업 문서). 빈칸 금지 — 단 "해당없음 + 근거"는 허용.
  - 불변식은 수용기준과 **분리**해 명시한다(동시성·순서·금액 보존 등 예시기반 테스트가 놓치는 속성).
- **유닛 테스트 필수.** 통합 테스트는 로컬로 검증 가능한 부분을 덮는다. 불가분은 "왜 불가"를 명시.
- **DB 스키마·인덱스 변경 시 부하/시뮬레이션 점검** — 대량 데이터·동시성에서 쿼리/락이 버티는지 확인(앱테크는 적립·출금 동시성이 핵심이라 특히 중요).
- 적대적 검증·보안 점검을 **무엇을 어떻게 확인했는지** PR에 남긴다.

## 게이트 (커밋/PR 전)
1. 수용기준·불변식·테스트 정의가 있고 빈칸 없음(근거 없는 "해당없음" 금지).
2. 유닛 테스트 실제 존재 + 통과 — **CI(`app`/`backend` 잡)가 강제**.
3. 통합 테스트: 로컬 docker로 가능한 부분 커버.
4. **적대적 QA**: "이 코드가 어떻게 깨지나"를 별도 컨텍스트로 점검(아래).
5. **보안 점검**: 인증/권한, 입력 검증, 잔액·금액 조작 가능성, 시크릿 노출.
→ 자가점검은 [`code-conventions`]·[`consistency-check`] 스킬. **최종 통과 판단은 사람(리뷰어).**

## 적대적 검증을 Claude로 하는 법
- 구현한 세션이 아니라 **새 세션/서브에이전트**에게 요청: "이 코드를 깨보라 / 이 불변식이 위반되는 입력·순서·동시성 시나리오를 찾아라."
- "통과"를 가정하지 말 것 — 반례·엣지케이스·경쟁 상태(예: 동시 출금 더블 스펜드, 중복 출석)를 **먼저** 찾게 한다.
- 발견된 케이스를 테스트로 고정한 뒤 수정한다.
